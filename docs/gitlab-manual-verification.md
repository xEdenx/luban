# 自部署 GitLab：无自动 CI 的验收路径

状态：第一版操作设计，尚未在团队 GitLab 验证。用户已确认无法自动触发 CI；GitLab 版本、许可、Runner、手动 Pipeline 和审批配置未知。

## 1. 第一版执行路径

```text
明确需求 → 风险分级 → 原生增量 Spec / Mini-Spec
  → 人工确认具体版本
  → Agent 通过既有客户端实现
  → 人工发起已有构建/测试命令
  → 保存被测版本、AC 对应结果、原始报告与剩余风险
  → GitLab MR Reviewer 核对
  → 有权限的人员按现有流程合并
```

不使用 GitHub 代管内部业务需求或验证报告。公开 GitHub 只分发通用标准；业务产物保留在内部 GitLab 或团队批准的位置。

## 2. 先核验权限，再决定门禁强度

| GitLab 实际能力 | 第一版做法 | 可以声称的约束 |
|---|---|---|
| 有受保护分支、合并人受限 | 指定合并人检查 Spec/证据和 Review | 合并权限受控；测试是否通过由人工核验 |
| 有所需强制审批能力 | 启用并验证审批规则、变更后失效等实际支持项 | 对已验证配置声称审批门禁 |
| 只有可选 approval / 评论 | 记录人工批准版本，指定合并人遵循操作规则 | 人工流程约束，不能称自动阻断 |
| 可以手动运行 Pipeline 且有 Runner | 经授权后复用同一验证命令与报告 | 实际运行通过后才声称平台执行 |
| 无 Runner 或 Pipeline 不可用 | 本地运行项目现有测试，Reviewer 查原始结果 | 本地执行 + 人工合并核验 |
| 无保护分支且任何人可合并 | 先验证流程价值，明确需要负责人补权限或接受限制 | 不能保证流程强制执行 |

官方当前文档区分可选与必需审批；具体能力取决于 GitLab tier 和配置，工作环境必须按实际版本核验，不能因自部署就推断拥有全部能力。[审批](https://docs.gitlab.com/user/project/merge_requests/approvals/)、[保护分支](https://docs.gitlab.com/user/project/repository/branches/protected/)

## 3. 手动验收步骤

1. 在工作电脑打开正确业务仓库和分支，检查当前提交与工作区状态。优先使用干净提交；测试过程中也可能生成文件，需辨别是否影响被测内容。
2. 对照已确认 Spec/AC 版本，检查本轮需要执行的测试与人工项。先使用项目已有命令，不直接运行未知脚本。
3. 在允许的环境执行构建/测试，保存完整退出状态和原始报告。不要只截取“成功”一行；敏感日志保留在内部。
4. 核对每个必需 AC 是否实际验证；失败、跳过、零测试、缺报告、手工未执行项分别记录。
5. 记录被测 SHA、分支/目标基线、Spec/AC 文件摘要、依赖/环境要点与时间。若脏工作区参与测试，commit SHA 本身不足以表示实际输入，应保存内部 diff/文件清单，或提交后重跑。
6. 将证据放在团队批准位置，在 Implementation MR 引用。作者记录执行结果，Reviewer 独立检查语义与结果。
7. Reviewer 检查 MR head 与被测版本关系。测试之后改变代码、测试、依赖、配置或 AC 时，要求重新执行受影响验证。
8. 合并人检查批准依据、证据、人工验收和未解决风险，再按现有权限合并。未完成验收不以 Agent 宣称完成代替。

## 4. 最小证据模板

Java/Maven 默认布局可试用 [AC 检查器](../scripts/README.md)生成机器部分；人工项和审核仍使用 [验收记录模板](../templates/verification-record.md)，至少填写：变更 ID、等级、需求确认链接、被测提交与工作区状态、Spec/AC 版本、运行命令/退出码、原始报告链接、AC 结果、人工项、未验证风险、Reviewer 与合并前版本核对。

文件摘要用于识别内容是否变化，不证明人工审批真实性；截图与本地报告也不能独立证明无人修改。可信度依赖内部存储、审核身份、复跑与平台权限。高风险任务按需由 Reviewer 在允许环境独立复跑关键验证。

## 5. 失败与恢复

- 业务规则不明确：暂停相关实现，补充 Spec/AC 并重新确认。
- 实现或测试失败：修复后重跑，不删减 AC 伪造通过。
- 环境不可用：标记 blocked/unverified，记录缺少的授权工具或资源，继续不依赖它的检查。
- 证据失效：重跑关联验证。不能把历史成功报告复制为本轮结果。
- 紧急修复：走团队负责人批准的例外，明确替代验证与补全时限。

## 6. 将来接入 CI 时保持什么不变

保留变更 ID、AC 语义、测试映射、报告格式和人工验收责任。只替换触发方式与证据保管入口。需要自动状态检查时再核验 GitLab/Runner 能力，不提前建设自动化基础设施。

# ADR-0005：业务变更与全局约束的混合生命周期

日期：2026-10-10。状态：已接受，用户已明确同意补充此约定。本决策补充 ADR-0001，保留其业务变更 Flow-forward 路线。

## 背景

业务变更需要保存每次增量的意图、批准与验收历史；全局原则、工程约束与长期设计需要表达当前有效规则。原设计已区分历史与当前知识，但尚未明确每类规则的权威来源、约束变更确认和历史验收使用的约束版本。

## 决策

- 业务变更使用 Flow-forward：活跃期间可修订并重新确认，完成后冻结，新需求新建记录。
- 全局约束与长期设计采用 Living Spec 式持续维护：每类规则只有一个权威来源，修改先确认，再同步受影响的方案、实现、测试与引用。业务工程复用 Constitution、工程规范及现有设计；鲁班标准仓库复用主技术设计与团队操作基线。
- AGENTS.md 与 Skills 负责规则引用及执行，项目记忆负责事实与进度；单次任务不能隐式覆盖全局约束，冲突由对应规则负责人裁决，相关实施先暂停。
- 确认与验收引用适用约束的路径、条款和具体提交或可复核快照。规则实质变化影响活跃任务时重新确认与验证；历史批准和验收保留当时基线。
- ADR 保留历史，以新记录明确补充或取代关系；当前结论同步到长期设计。

## 后果与边界

复用现有 Git、MR、工作说明及验收模板，L0–L3 和单/双 MR 路径继续适用。无需增加全量业务 Spec、第二套状态系统或版本服务。

本次明确文档与共享入口约定，未增加机器门禁。约束基线由 Reviewer 人工核对，acceptance.json 0.1 与检查器保持原有能力；真实客户端行为与团队环境执行仍待验证。

官方允许按区域采用不同持久化模型；将 Living Spec 的维护原则应用到长期工程文档是团队约定。[固定版本来源](https://github.com/github/spec-kit/blob/959e866caa3618bf3dc290d5dca33394365af9c6/docs/concepts/spec-persistence.md)。具体规则以[主设计第 4 节](../technical-design.md#4-混合生命周期flow-forward-与-living-spec)为准，前序决策见 [ADR-0001](0001-native-first-flow-forward.md)。

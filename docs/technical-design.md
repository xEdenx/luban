# Agent-Native Development 团队转型方案

版本：0.3 · 决策基线与实施设计 · 2026-10-10（Asia/Shanghai）
配套文件：[Codex 实施任务接力说明](implementation-handoff.md)

> **以 Spec Kit 原生能力为基础，选择 Flow-forward Spec 作为生命周期策略，保留四级任务模型，以 AC-to-Test 的可执行验收为核心扩展，最后通过官方 Bundle 机制实现团队标准化推广。**

本文承接《团队AI开发方案推荐》中的最终用户决策，作为后续工程落地的主设计依据。本仓库已完成部分 T0 核验与 T2 实验原型；实际状态以 [项目记忆](memory.md) 和 [原生能力核验](research/native-capability-audit.md) 为准，尚未修改团队插件或启用业务工程门禁。文中的示例、建议阈值和实施路径不表示已上线。

## 1. 目标与适用范围

团队希望将现有 Spec Coding 方式升级为 Agent-Native Development：由 Agent 理解工程、发起需求澄清和结构化 Spec，开发者补充业务规则并确认，再由 Agent 实现、运行验证，最终通过自动化验收与人工业务逻辑审核完成交付。

需要解决的实际问题是：大需求最初生成 Spec，后续小需求和 Bug 通过 Chat 直接修改代码，历史 Spec 未同步，逐渐与系统脱节。解决方向是保存每次变更的意图与证据，同时明确当前工程知识的维护责任。

方案同时适用于刚开始的新工程与进行中的存量工程。现有工具为：

- 基于 Continue 自研的 VS Code 插件。
- Qoder 独立 Coding Agent App。

统一的是变更产物、验收契约和交付门禁。两种工具的接入方式分别验证，保留工具选择空间。

转型指标以 **Agent 自主交付率和交付质量** 为主，并同时观察总耗时、人工投入和维护成本。

### 2.4 已确认的落地环境与阶段调整

用户已确认：当前在个人电脑整理方案；后续将通用材料发布到 GitHub public repo，再通过允许的方式下载到受 MDM 管控的工作 MacBook 验证。团队业务工程使用自部署 GitLab，无法自动触发 CI。

因此，本仓库优先完成可迁移的设计、默认规则、模板与验证手册；个人电脑上的运行结果仅证明实验环境可行，不能代替工作电脑、真实插件和 GitLab 的验证。GitHub 用于公开通用标准，内部 GitLab 保存业务变更、审批和验收证据；两者不做业务资料同步。

第一版使用“人工运行项目已有验证命令 → 保存与被测版本绑定的报告 → Reviewer 核对 → GitLab MR 合并”的路径。下文 CI 的确定性检查要求继续作为目标契约，当前先由人工触发相同验证，不声称已启用自动流水线或强制状态检查。手动流水线、Runner、GitLab 版本/许可和保护分支能力均待工作环境核验。

在无自动 CI 的条件下，AC-to-Test 仍可执行，但证据可信度依赖可复核原始报告、执行人记录和独立 Review。权限门禁与自动门禁分开报告，不开发自建 CI 服务弥补此限制。

具体执行见 [GitLab 手动验收路径](gitlab-manual-verification.md) 和 [工作电脑验证手册](work-mac-validation.md)。本节为当前落地约束，优先于下文尚未配置的自动 CI 目标。

## 3. 架构与原生能力复用边界

| 层 | 首选能力 | 团队补充的内容 |
|---|---|---|
| 需求、规划与任务 | Spec Kit Specify、Clarify、Plan、Tasks、Analyze、Implement、Converge | 风险分级、验收字段及人工确认约定 |
| 模板裁剪 | 官方模板 / Lean Preset / Preset 机制 | 必要的团队字段，避免复制整套命令 |
| 流程组织 | Workflow 与官方 Bug 流程 | 按等级组合步骤、连接实际审批记录 |
| 工具连接 | 原生 Integration；必要时 generic | Continue 自研插件与 Qoder App 的薄适配 |
| 工程原则 | Constitution | 项目长期架构、兼容性、安全和测试原则 |
| Agent 工作方式 | AGENTS.md + Skills | 项目入口、执行命令、专项操作知识 |
| 可执行验收 | 现有测试框架与 CI 报告 | AC 映射及证据完整性检查 |
| 交付控制 | Git 平台权限、Review、现有 CI/CD | 必需检查、审批规则、例外审计 |
| 标准分发 | 官方 Bundle | 经试点验证的内部组件组合与版本策略 |

Spec Kit 的 CLI 管理初始化、集成和流程组件；Coding Agent 执行安装后的指令或 Skills。不能假设每个 `/speckit.*` 命令都是独立执行代码生成的终端命令。实际入口名称以生成文件和工具验证结果为准。

Flow-forward、L0–L3、审批权限、AC 映射和 CI 规则共同形成团队约定。其中 L0–L3 和本文的 AC 映射格式是团队设计，不声称为 Spec Kit 内置标准。

OpenAI 官方实践展示了仓库内 AGENTS.md、Skills 与 CI 的协作方式；本文采用其工程思路，不要求迁移团队工具到 Codex，也不把本方案称为 OpenAI 官方认证的方法。[官方实践](https://developers.openai.com/blog/skills-agents-sdk)、[开放 Harness 的职责](https://developers.openai.com/blog/codex-as-a-platform)

### 避免重复建设

先检查当前版本的 Core、Lean、Bug、Workflow、Preset、Integration 是否已经覆盖需求。确有差距才新增 AC 报告检查或工具入口适配。每项新增能力应说明原生能力不足在哪里、谁维护、如何退出。

初期不建设中央 Agent 编排器、新 Spec 引擎、第二套任务状态系统、全量知识库或专属研发门户。现有 Issue/PR、Spec Kit 产物与 CI 足以承担第一轮闭环。

## 4. Flow-forward Spec 生命周期

### 4.1 当前知识与历史意图区分

| 内容 | 生命周期 | 后续需求如何使用 |
|---|---|---|
| 当前代码、自动化测试、接口契约、数据库迁移 | 随系统演进维护 | 判断当前实现与受约束行为，仍需检查覆盖盲区 |
| 当前架构、ADR、Constitution、工程规范 | 长期维护 | 提供仍然有效的决策与边界 |
| 活跃变更的 spec / plan / tasks | 当前变更期间维护 | 作为本轮人工确认的意图与实施依据 |
| 已完成变更的 Spec 与验收记录 | 保存为历史 | 用于审计、追溯和解释；不直接当作当前功能说明 |

发现代码、测试和当前契约相互矛盾时，由负责人澄清，不能简单宣布“代码就是正确需求”。

### 4.2 规则

1. L1–L3 每项有边界的变更创建新 feature 目录；L0 可以只使用 Issue/PR 中的 Mini-Spec。
2. Agent 根据当前工程起草 Spec，列出未知业务规则，开发者补充并确认。
3. 尚未完成的变更允许修订。修改范围、AC、风险等级或关键设计后，重新执行受影响的分析与审批。
4. 合并前让 Spec、Plan、Tasks、代码及验收证据对齐；保留未验证项及处理决定。
5. 合并后的变更产物冻结为历史，归档可以仅是状态/链接约定，无需移动文件或新增归档引擎。
6. 后续变更新建记录，通过关联 Issue、PR、前序变更 ID 表达延续关系，不修改旧记录来伪装成最新系统规格。
7. 需要长期保留的架构决策、API 契约和业务约束迁入现有长期知识位置，并随实现更新。

完成后发现错误，用新变更和更正链接说明；不覆盖原审批与证据。取消的变更保留取消原因，不计入已交付。

官方资料支持完成产物作为历史、新需求新建目录的模型；本团队再补充审批、AC 与冻结约定。[生命周期依据](https://github.com/github/spec-kit/blob/main/docs/concepts/spec-persistence.md)、[变更维护指南](https://github.com/github/spec-kit/blob/main/docs/guides/evolving-specs.md)

## 5. L0–L3 风险分级与工作流

以下为已确定四级模型的**初始操作建议**；负责人权限已确认，具体身份、阈值和例外细则在试点中明确。等级按最大风险判断，不按代码行数判断。

| 等级 | 典型边界 | 最小产物 | 实施路径与人工确认 |
|---|---|---|---|
| L0 | 低风险局部修复、文案、无行为变化的小调整 | Mini-Spec、验证依据、PR | 影响分析 → 简短确认 → 实现/验证 → 人工 Review；Bug 优先评估官方 Bug 流程 |
| L1 | 边界清楚、单模块常规业务需求 | 增量 Spec、精简 Plan/Tasks、AC 映射、证据 | Specify/必要澄清 → 人工确认 → Plan/Tasks → Implement → Converge → 手动验收（未来 CI）→ 人工逻辑验收 |
| L2 | 跨模块、接口演进、数据库结构、并发一致性等 | L1 + 明确技术方案及契约/集成验证 | 需求确认 + 技术方案确认；Analyze 后实现，交付前验证兼容性与影响面 |
| L3 | 支付资金、权限安全、不可逆数据操作、重大迁移等 | L2 + 专项风险、发布、预演与恢复方案 | 专项审批、分阶段实施、隔离验证，按权限执行发布及恢复演练 |

L0 不表示所有 Bug 都是低风险；一个权限判断的单行修复可能属于 L3。数据库结构变更初始按至少 L2 评估，破坏性迁移或敏感数据风险提升到 L3。

Agent 推荐等级并说明触发条件；L0/L1 由模块负责人确认，L2/L3 由技术负责人确认。发现新风险先停止相关实施并上报，补足所需确认后继续。降级必须由拟降级前等级对应的负责人确认并留痕；跨 L2/L3 降到 L0/L1 仍需技术负责人批准，不能只由 Agent 更改标签。

L0 的前置确认可以是已明确的 Issue 或开发者确认的短变更说明，不强制完整 Spec PR。L1–L3 在实现前确认需求；L2/L3 还应确认关键技术方案。减少的是形式成本，保留的是业务确认。

### L0 Mini-Spec 示例

```markdown
变更：修复订单查询在关联用户缺失时的异常。
等级：L0；依据：局部错误处理，不改变接口契约，不涉及权限和数据写入。
期望：返回已约定的业务错误，并保持已有正常查询行为。
范围外：不重构查询模块。
验收：新增缺失用户回归测试，运行已有查询测试。
确认：关联原始 Issue / 人工确认记录。
```

无行为变化的调整可以复用构建、静态检查和已有回归验证，不为每次文案修改机械新增测试。验证不适用时写明理由，由 Reviewer 确认。

## 6. 从需求到交付的闭环

```text
需求 / Bug
  → Agent 检索当前工程，提出影响面、等级、未知问题
  → Agent 起草增量 Spec / Mini-Spec 与 AC
  → 开发者补充业务规则并确认；复杂变更确认技术方案
  → 原生 Plan / Tasks / 必要 Analyze
  → Agent 实现代码与验收测试
  → Converge 检查遗漏，必要时回到 Implement
  → 人工触发已有测试与证据检查；将来可由 CI 执行同一契约
  → Reviewer 检查业务逻辑、测试有效性和剩余风险
  → 受保护流程合并 / 按等级发布
  → 冻结变更记录，更新长期知识，采集指标
```

前期分析与确认角色可按团队安排兼任；最终交付通常由另一位开发者审核，特殊情况明确记录例外。L3 另按团队职责安排专项审批。第一版不要求引入多个 Agent；如需独立模型 Review，也只是补充证据，不能替代人工和测试。

反馈分三类处理：实现遗漏回到 Implement；工程假设失效修订 Plan 并重新技术确认；业务规则变化修订 Spec/AC 并重新需求确认。禁止为了让测试通过而静默放宽 AC。

Converge 是原生的模型一致性检查，可追加未完成任务，再由 Implement 修复。它本身不代表测试已执行或所有行为已满足。[原生命令定义](https://github.com/github/spec-kit/blob/main/templates/commands/converge.md)

## 7. AC-to-Test 可执行验收

### 7.1 先确认语义，再检查映射

每个 AC 应表达可观察的业务结果，明确关键前置条件、触发动作、边界与异常。Agent 起草，业务负责人或开发者确认。测试至少覆盖变更的核心行为和必要回归，不以增加测试数量为目标。

例如“订单超过 30 分钟取消”还需要确认计时起点、恰好 30 分钟的边界、支付与取消竞争、重复调度、时区和失败重试。本文示例采用“创建后满 30 分钟且仍未支付”的假定，仅用于说明，不能直接带入真实业务。

### 7.2 最小机器映射实验实现

沿用原生 spec.md 的验收场景，增加稳定 AC ID，不再复制完整业务需求。面向已确认的 Java/Maven/Spring Boot，当前采用 acceptance.json 0.1 和 Python 标准库检查器；这是团队必要扩展，不是 Spec Kit 官方格式。早期 YAML 提案被本版 JSON 取代，不同时维护两套运行格式。

```json
{
  "schema_version": "0.1",
  "change_id": "fictional-order-timeout",
  "risk_level": "L1",
  "spec": "spec.md",
  "report_sets": [{"module": ".", "kind": "surefire"}],
  "criteria": [{
    "id": "AC-001", "kind": "automated",
    "tests": [{"module": ".", "kind": "surefire", "class": "example.OrderTimeoutTest", "name": "cancelsExpiredOrder"}]
  }]
}
```

Spec 保存 AC 的完整含义；映射只引用 AC 和实际 XML testcase 身份；执行结果记录本次事实。人工项使用 kind=manual 并说明 reason/procedure，结果、执行人与时间另留内部审核记录，不能靠修改 JSON 宣称通过。

默认运行模式核对干净提交、Spec/映射摘要、明确命令的退出码、报告新鲜度和逐 AC 结果。报告读取模式只用于诊断；任何自动结果都不自动批准交付。完整规则、虚构示例和实际操作分别见 [验收契约](acceptance-contract.md)、[样例](../examples/maven-acceptance/acceptance.json)和[操作说明](../scripts/README.md)。原型自检不等于真实 Spring Boot/Maven 工程验证。

### 7.3 验收执行器应验证的事实

| 检查 | 合格条件 |
|---|---|
| AC 完整性 | 已确认 Spec 中的所有必需 AC 都有验证方式；无重复、悬空或遗漏 ID |
| 测试映射 | 选择器可以定位到实际结果；多模块、参数化测试的标识规则明确 |
| 实际执行 | 读取本次运行的测试报告；只存在测试源码或测试名称不算执行 |
| 结果 | 必需测试均通过；失败、跳过、零测试、缺失报告均不得记为成功 |
| 证据新鲜度 | 对应当前被检查的代码提交、Spec/映射版本、CI run 与测试环境 |
| 人工项 | 由规定角色提供可核验记录；未完成不得混入自动验收成功数 |

首版读取 Maven Surefire/Failsafe 默认布局的 XML，使用实际 classname/name 精确匹配；JUnit 与插件精确版本、参数化测试及自定义布局仍待现场核验。其他语言暂不实现适配，不迁移现有测试框架。

第一版证据清单可以只记录 change ID、被测 commit SHA、Spec/AC 摘要或版本、本地运行记录或 CI run 链接、测试报告链接、未验证项和人工验收链接。当前由手动运行生成并在内部保管，未来可交给 CI，不新增复杂证据服务。

注意 CI 可能测试 PR 的合成合并提交，应记录实际被测 SHA 和对应 PR head/base，不能把两者混为一谈。后续实现变动使原有证据失效，重新执行相关验证。

### 7.4 映射不等于正确性证明

AC 与测试一一对应只能证明可追溯，不能证明断言有效。Reviewer 应检查测试是否真正表达已确认业务规则、是否覆盖风险边界，以及是否与实现一起犯了相同的理解错误。

行为缺陷尽可能保留“修复前复现失败、修复后通过”的证据。涉及外部环境或人工操作时明确验证边界。测试失败时修实现或重新澄清需求，不以删除测试、跳过场景、降低断言作为默认解决办法。

## 8. 人工确认与软件门禁

### 8.1 四道 Gate

| Gate | 检查内容 | 实现载体 |
|---|---|---|
| G1 变更完整性 | 等级、范围、AC、关键问题、必要设计齐备 | 原生分析 + 最小结构检查；L0 检查 Mini-Spec |
| G2 实现前确认 | 指定人员确认具体 Spec/AC；L2/L3 确认方案 | Workflow 暂停辅助操作；Git 审批或可信审批记录提供凭证 |
| G3 自动化验收 | 测试、现有质量检查、AC 结果与证据完整性 | 当前手动运行 + 人工核验，未来接 CI 状态检查 |
| G4 业务逻辑验收 | 业务语义、边界、测试有效性、剩余风险 | 人工 Review、Code Owner 或平台对应机制 |

### 8.2 “限制”的不同强度必须说清楚

- AGENTS.md / Skill：模型可读的工作约定，不能单独保证强制执行。
- Workflow gate：流程暂停与恢复；本地状态或输入若由执行者控制，不能等同于可信审批。
- 受保护 Git 分支与必需 CI/Review：限制交付和合并；实际有效性取决于平台配置、审批人身份及管理员/机器人绕过权限。
- 工具写权限或受控执行环境：若要求未经审批绝对不能写业务代码，需要额外控制实际执行权限。

官方 Workflow 允许通过输入提供 gate 结果，且 shell 步骤不自带能力沙箱。因此不得把本地 `approved` 字段或可由 Agent 提交的 gate 输入当作独立人工授权证明。[Workflow 边界](https://github.github.com/spec-kit/reference/workflows.html)

CI 能阻止不合格代码合并，通常不能证明开发者在本地何时生成了代码。本文的目标是“确认后开展实施，并强制检查交付依据”；若团队需要严格的写入前授权，在工具兼容试点中验证实现方式，未验证前不作保证。

### 8.3 已确认的审批路径

| 等级 | 路径 | 必须保留的边界 |
|---|---|---|
| L0 | 单 PR + Mini-Spec + 人工 Review | Chat 也要留下意图和验证，不允许无记录交付 |
| L1 | 已决定单 MR 分阶段：先确认 Spec/AC 版本，再实现，最后审核 | 缺少可信版本绑定与权限控制时，仅能称协作约定 |
| L2 | 单 MR 分阶段，确认 Spec/AC 与技术方案后实施 | 明确确认人和内容版本，变更后重新确认 |
| L3 | Spec MR → 实现 MR | 引用已批准 Spec/方案确切版本，按风险补专项确认 |

L3 双 MR 复用原生 Git 审核能力，先合入 Spec/Plan/AC，再开始实现 MR；它提供明确的批准基线，但仍不证明本地代码生成的物理时间。

如果采用单 PR 强门禁，审批必须绑定 Spec/AC 的具体内容版本，并由可信身份产生，关键内容修改后审批失效。先评估平台原生审核能否满足，再考虑最小检查脚本；不默认开发审批服务。

必需检查及其配置也要纳入权限保护。项目若缺少相应平台能力，应明确只能执行哪部分软约束，不宣称“不可绕过”。紧急修复通过指定负责人批准例外，记录风险、验证与补全时限，不能静默删除检查。

## 9. AGENTS.md、Skills 与工程知识的职责

| 载体 | 内容 | 维护方式 |
|---|---|---|
| Constitution | 长期工程原则与底线 | 人工确认，复用项目已有规范 |
| AGENTS.md | 导航、当前变更定位、常用验证入口、审批和历史 Spec 使用约定 | 精简，链接到详细规则 |
| Skills | 专项操作知识、脚本和参考资料 | 按需加载，先复用原生流程 |
| Spec / Plan / Tasks | 本次意图、设计和实施工作 | 活跃期间同步，完成后冻结 |
| 测试 / CI / 接口契约 | 可执行的行为和约束 | 随实现维护，报告实际验证结果 |
| 架构文档 / ADR | 仍有效的设计与决策缘由 | 按影响更新，不重复全部 Spec |
| 项目 memory / 交接记录 | 可继续工作的状态、链接和未决问题 | 指向权威产物，避免复制需求 |

初期优先补充 `acceptance-verification` 这类原生能力未覆盖的专项内容，数据库迁移等 Skill 按真实需求增加。不另写一套 Specify、Plan、Implement Skill 来复制 Spec Kit。

`.agents/skills/` 可以作为团队共享内容候选位置，但不能假定所有工具自动读取；原生生成目录与项目既有位置优先。Continue Rules 和 Qoder 的入口应引用或受控分发同一来源，明确生成文件归属，避免手工维护两份规范。

### 建议目录：按实际初始化结果调整

```text
repo/
├── .specify/                      # Spec Kit 管理；具体布局由版本决定
│   └── memory/constitution.md
├── specs/<feature>/
│   ├── spec.md
│   ├── plan.md
│   ├── tasks.md
│   └── acceptance.json             # 团队扩展 0.1，非官方默认
├── AGENTS.md
├── .agents/skills/                 # 候选共享位置，需验证加载/分发
├── .continue/rules/                # 自研插件保留该机制时使用
├── docs/                          # 复用现有架构、ADR、交接文档
└── <已有 CI 配置与检查脚本目录>
```

不默认创建 `.agent-native/` 或另一个 `changes/` 目录。L0 记录可以留在 PR，Bug 产物沿用官方扩展实际生成的位置。此图不代表安装器会自动创建所有内容。

## 10. Continue 自研插件与 Qoder App 接入

### 10.1 Continue 自研插件

上游 Rules 文档描述 `.continue/rules/`，Prompts 提供复用入口；自研插件是否具备这些能力，取决于采用的上游版本和修改内容。[Rules](https://docs.continue.dev/customize/deep-dives/rules)、[Prompts](https://docs.continue.dev/customize/deep-dives/prompts)

先检查真实插件，尝试直接加载原生生成指令或引用其文件。如果需要入口包装，仅连接“起草/澄清 → 实现 → 验证”，保持原生产物和语义，不复制流程逻辑。

### 10.2 Qoder 独立 Coding Agent App

官方明确新的 Qoder 是独立桌面产品，与 Qoder IDE 并存；对应的 App Skills 文档描述安装、导入和显式调用。[产品边界](https://docs.qoder.com/qoder/overview)、[App Skills](https://docs.qoder.com/qoder/skills)

Spec Kit 中的 `qodercli` 针对 Qoder CLI；Qoder IDE 或 QoderWork 的文档不能直接证明独立 Coding App 的行为。先核对实际产品、版本及其文档，再验证导入包、项目作用域、引用文件解析和执行权限。

### 10.3 最小兼容性试验

两种工具分别记录产品/插件版本、操作步骤、生成文件、运行结果和限制：

| 试验 | 通过标准 |
|---|---|
| 发现原生指令 / Skill | 新会话中实际可见并能调用；不只检查文件存在 |
| 读取工程规范 | 能按真实加载机制读取 Constitution、AGENTS.md 或适配入口 |
| 定位活跃变更 | 选择正确 Spec，能区分历史记录；多分支切换后仍正确 |
| 澄清与人工确认 | 能展示未知问题并暂停；恢复后保留正确上下文与批准版本 |
| 实施与执行测试 | 在正确工作区运行原有命令，保留退出结果和报告 |
| 路径与辅助脚本 | 相对路径、参数、脚本解释器在实际平台可用 |
| 跨工具接力 | 另一工具读取仓库产物继续工作，无需复制原聊天记录 |
| 升级与卸载 | 不覆盖项目规则，能识别受管文件并恢复试点前状态 |

原生集成不适用时，先评估 `generic` 的命令或 Skills 输出。官方当前文档说明 generic 支持自定义目录及 Skills 布局，但不会自动让任意 App 识别这些文件。[集成依据](https://github.github.com/spec-kit/reference/integrations.html)

试点不能完成的操作明确标为“未验证/受限”，允许通过显式读取原生指令和人工操作先验证流程价值；不得把这种方式计为自动集成成功。

## 11. 新工程与存量工程接入

### 存量工程

先确认工作区状态与现有工程规范，在隔离分支或测试副本中初始化；预览受影响文件，保留已有配置。不要直接在主分支使用可能覆盖文件的初始化选项。

复用已有构建、CI、测试、架构与 ADR；补充最小 Constitution/Agent 入口和必要 AC 检查。从下一项边界清楚的真实变更开始，不逆向补写全系统 Spec，也不一次性整理全部历史需求。

官方存量项目指南支持从有边界的后续变更切入。[接入指南](https://github.github.com/spec-kit/guides/existing-projects.html)

### 新工程

先确立技术栈、模块边界、基础质量检查和最小架构，再引入 Spec Kit 与 Agent 入口。首个基础能力可按 L2 评估，后续逐项分级，避免将“新工程”直接等同于“每项都是高风险”。

两类工程都检查 Agent 指南、项目交接记录、技术设计、ADR 是否已有等价载体。缺失时按适用性补充或记录例外，避免为了目录标准创建空文档。本次只有设计交付，决策直接收录在本文，不另建一套仓库治理文件。

## 12. 分阶段实施与退出条件

阶段按验证结果推进，时间为规划建议。可把约六周作为首轮试点窗口，不作为交付承诺。

| 阶段 | 工作 | 进入下一阶段的条件 |
|---|---|---|
| P0 盘点与版本核验 | 确认仓库、平台、两种工具版本；核验原生能力与受管文件 | 事实表、兼容矩阵、精确版本及最小差距清楚 |
| P1 原生最小闭环 | 一个存量工程，跑 L0 与 L1；复用 Core/Bug/Lean 的适用能力 | 人工确认 → Agent 实现 → 测试 → Review 可追溯，无自研框架 |
| P2 可执行验收与门禁 | 最小 AC 映射、报告检查、手动验收与 Review；补一个 L2 案例 | 正常变更可交付；缺 AC、跳过测试、过期证据等负例被拦截 |
| P3 工具接入与新工程验证 | 在 Continue 自研插件与 Qoder App 分别操作；新工程接入 | 两个真实客户端完成闭环和跨工具接力，明确剩余限制 |
| P4 团队标准分发 | 封装验证过的 Preset/Workflow/必要 Extension，再用 Bundle 组合 | 可安装、升级、移除并保护项目定制，有版本与回退说明 |
| P5 推广与迭代 | 按风险扩展试点，定期回顾成本、质量及模型变化 | 指标支持扩大推广，维护责任与支持边界明确 |

L2/L3 从试点起保留专项审批边界。L3 的生产发布与数据操作按现有授权独立执行；开发流程跑通不代表生产权限已验证。

试点若发现流程成本明显增加而质量无改善，应删减无效步骤。兼容性不足时保留仓库产物和 CI，调整入口；不通过复制另一套流程解决。

## 13. Bundle 标准化策略

官方 Bundle 是已有 extensions、presets、workflows、steps 的版本化组合与分发层，本身不增加新的运行时能力。[官方机制](https://github.com/github/spec-kit/blob/main/docs/reference/bundles.md)

未来团队 Bundle 可组合官方 Bug 组件、团队最小 Preset、按风险组织的 Workflow，以及确有必要的 AC 检查 Extension。名称如 `backend-agent-native-sdlc` 只是内部候选，不是已存在的软件包。

不要默认把任意 Skills、AGENTS.md、CI 文件或 Spec Kit Core 当作独立的 Bundle 组件类型。核验锁定版本的 schema、组件挂载与文件归属，使用受支持的承载方式；Core/CLI 作为基础依赖单独锁定。两种客户端的安装步骤按实际能力分别提供。

发布前完成以下验证：

- 固定 CLI、组件与集成版本，记录来源、兼容范围、发布说明。
- 预览将安装及修改的文件；区分团队受管内容与项目自主维护内容。
- 在新工程与存量工程验证安装、重复安装、升级、移除及故障恢复。
- 不把安装幂等理解为更新原子化；先确认失败时会留下什么状态，依赖 Git 快照保留恢复路径。
- 不覆盖项目 Constitution、业务 Spec、架构文档和手工规则；必要变更通过审查合并。
- 发布最小使用说明与支持责任，保留版本回退能力。

## 14. 试点评估与主要风险

### 指标定义提案

| 指标 | 初始口径 |
|---|---|
| Agent 自主交付率 | 进入实施的合格任务中，Agent 完成主要实现和验证，且无需人工直接修改代码/测试或接管实施，并通过实际自动化检查与人工验收的任务占比（当前手动触发，未来可接 CI） |
| 人工干预成本 | 记录计划内需求澄清/审批，与非计划纠错/代码接管的次数及人时 |
| 首轮验收通过率 | 首次提交验收后无需实现返工即通过的比例 |
| 交付质量 | 按等级观察回归、逃逸缺陷、回滚与线上问题；固定统计窗口 |
| 端到端成本 | 从需求接收到可交付的耗时，另记 Spec 确认到交付耗时、等待时间和算力费用 |
| 证据与流程成本 | AC 验证完整性、缺失证据比例、维护模板/适配器和检查脚本的投入 |

必要的人工作业确认不自动算作 Agent 失败。按 L0–L3、工具版本、任务类型比较，不用大量简单任务稀释高风险结果。先采集基线，不预设提升百分比；AC 映射率不能替代缺陷指标。

### 风险与处理

| 风险 | 处理 |
|---|---|
| 历史 Spec 被当作当前需求 | 明确生命周期、活跃变更入口和前序链接；更新长期契约 |
| 小任务绕过记录 | PR Mini-Spec 与风险确认纳入最小门禁 |
| 文档与流程膨胀 | 按等级裁剪，复用官方模板；每个扩展证明必要性 |
| 审批由 Agent 自证 | 使用可信平台记录；绑定具体内容版本并检查修改后的失效 |
| 测试只验证实现细节 | 人工审查 AC 与断言语义，缺陷优先保留失败复现证据 |
| CLI 与 App 能力混同 | 按真实产品与版本逐一试验，不以另一产品结果代替 |
| 上游升级覆盖定制 | 使用原生扩展机制、受管文件清单和升级演练 |
| 过早自动发布高风险变更 | 保留现有发布权限与专项审批，隔离环境验证 |

## 15. 第一版完成标准与接力入口

工程试点只有满足以下条件，才可称为第一版落地完成：

- 锁定版本，说明原生复用能力、团队新增内容及待验证边界。
- L0 留有 Mini-Spec；L1–L3 按风险确认 Spec/方案，能追溯具体审批依据。
- 至少在一个真实存量工程和一个新工程验证接入；两种实际客户端分别验证，不用 CLI 替代 App。
- AC 能关联本次实际测试结果，关键负例验证门禁确实失败；人工项独立记录。
- 代码、测试、Spec、长期文档和验收证据对齐；已完成 Spec 作为历史保存。
- 已说明权限、例外、维护责任和指标采集方式；未验证的能力仍显式保留。

Bundle 是后续标准化阶段的完成项，不是证明初期闭环可行的前置条件。完整推广完成时，再要求版本化 Bundle 及其安装、升级、移除和恢复验证。

# 开发者使用说明：提交需求，让 Agent 推进 L0～L3 工作流

版本：0.3 · 2026-10-10。日常开发从本页开始；维护者首次接入见 [Spec Kit 与 Skill 接入说明](skill-integration.md)。

## 1. 你需要做什么

**调用统一入口，提供需求文档或功能变化描述；Agent 先结合工程评估风险，再生成相应深度的规范产物，在关键节点请对应人员确认，确认后自动继续规划、编码和测试，最后请你核对功能与交付。开发者无需预先评级。**

不要求你先手写 Spec/Plan/Tasks、逐节填模板或逐条执行 Specify/Plan/Implement。现有需求不完整也可以开始；Agent 会查当前工程，集中提出影响业务正确性的必要问题。

当前已实现 Spec Kit 原生 team-sdlc Extension 0.1.1，安装后生成一个统一入口与四个兼容入口。个人电脑已验证安装与文件注册，**Continue 自研插件、Qoder 独立 App 的发现、调用及端到端行为仍待验证**。这是可安装的试点入口，不是已经在团队环境跑通的自动化承诺。

## 2. 默认调用统一入口，不先选等级

工程维护者先完成一次接入。之后选择 `speckit-team-sdlc-start`，按客户端已验证的方式调用/引用，提供需求即可。Agent 调查影响面、按团队规则建议等级，再由对应负责人确认；不能完全依靠任务作者自行评级。

原有四个入口继续保留，适用于已有任务接力或显式建议路径；**它们也必须执行同一风险评估，不能作为降级或绕过确认的通道**。以下为 generic Skills 模式实际生成的名称：

| 入口 | 适用任务 | Agent 自动准备 | 你负责确认 | MR 路径 |
|---|---|---|---|---|
| speckit-team-sdlc-l0 | 局部、可逆、不改业务契约的修复/调整 | 影响分析、Mini-Spec、验证方案 | 模块负责人确认等级，开发者确认意图 | 单 MR |
| speckit-team-sdlc-l1 | 单模块常规行为变更 | 原生增量 Spec、带 ID 的 AC | 模块负责人确认等级，业务/模块负责人确认 Spec/AC | 单 MR 分阶段 |
| speckit-team-sdlc-l2 | 跨模块、接口、结构、并发一致性 | 原生 Spec/AC、技术方案与影响面 | 技术负责人确认等级/方案，业务角色确认需求 | 单 MR 分阶段 |
| speckit-team-sdlc-l3 | 权限、资金、敏感数据、不可逆操作、重大迁移 | Spec MR 产物及专项风险、预演/恢复方案 | 适用角色确认，Spec MR 批准并合入 | Spec MR + 实现 MR |

评级遵循“工程证据 + 规则下限 + Agent 建议 + 负责人确认 + Review 复核”：权限/资金/敏感数据/不可逆操作等按 L3；公共接口、数据库结构、跨模块或一致性等至少 L2；一般行为变化至少 L1；L0 必须有局部、可逆且排除更高风险的依据。多个条件取最高，不按行数或“只是 Bug”降级。

Agent 必须展示依据、已检查/未检查的影响、未知项及建议等级。关键风险未知先查清；不把未发现当作已排除。Plan、实施新发现和最终 diff 都要复评；升风险先停相关实施，降级由降级前等级对应负责人留痕。具体规则见 [团队操作基线](team-operating-profile.md)。

名称不是跨客户端通用的终端命令。若客户端支持 Skill 菜单就选 Skill；若只能手动引用，明确引用工程内生成的 SKILL.md 并让 Agent 执行，不把“贴一个名称”当作调用成功。

## 3. 提供需求后，整个流程怎样执行

在已接入的业务工程选择统一 Skill，然后提供文档路径或直接描述，例如：

```text
使用 speckit-team-sdlc-start 处理这次需求。
需求文档是 docs/requirements/query-filter.md，请结合当前代码与测试读取。
这是本次增量变化，不需要重写已有系统的全部规格。
```

没有文档时也可以：

```text
使用 speckit-team-sdlc-start。
本次变化：在现有列表查询里增加按状态过滤，未传状态时保持原有行为。
请检查当前实现和接口，先指出需要我确认的边界，再生成本轮 Spec/AC。
```

这是虚构示例，不代表真实业务已批准。Agent 接下来应当：

| 阶段 | Agent 实际执行 | 人工参与与产物 |
|---|---|---|
| 1. 需求与工程调查 | 读取文档、AGENTS/Constitution、相关代码/调用点、接口/数据/测试；集中澄清关键未知 | 提供真实业务规则；留下输入依据与未决问题 |
| 2. 风险评估与路由 | 逐项核查高风险，按最高命中规则建议等级，解释依据和未检查项 | 对应负责人确认等级，可与下一阶段内容一起确认；无需任务作者自己打分 |
| 3. 规范化需求 | L0 起草 Mini-Spec；L1～L3 调用原生 Specify/必要 Clarify，生成增量 Spec 与稳定 AC ID；L2/L3 起草所需 Plan | 展示目标、范围外、边界、风险、AC 和具体版本；你纠正不准确内容，同一活跃变更持续修订 |
| 4. 开工确认 | 核对确认来源、角色、范围与版本；不足时保持暂停 | L0/L1 模块负责人；L2/L3 技术负责人及适用业务角色。L3 还需 Spec MR 批准并合入的基线 |
| 5. 自动实施 | 确认后补齐原生 Plan/Tasks/必要 Analyze，调用 Implement，编写/复用真实测试 | 一般无需逐步操作；新增业务疑问、关键方案变化或风险升级才重新确认 |
| 6. 自动验收 | 显式 Converge，执行实际 Maven 测试，建立 AC-to-Test 映射并检查报告；在已确认范围内修复重跑 | 产出版本绑定证据、逐 AC 结果、失败/跳过/未验证项；不能自称业务已验收 |
| 7. 人工核对与交付 | 准备功能核对步骤、MR 草稿，复评实际 diff，保留 Spec 历史并同步长期设计 | 开发者验证实际功能，通常另一位开发者复核等级、逻辑和证据；按平台权限合并 |

当前入口是会话内 Skill：它让正在使用的 Agent 实际执行这些阶段，没有另起一个后台开发服务。Spec Kit 提供原生能力，团队入口负责衔接、风险与确认规则，检查器验证报告；不是一个确定性引擎在后台保证所有阶段必然成功。

它应实际生成文件、实施代码和执行验证；只列出“你接下来运行这些命令”不算本阶段完成。

## 4. 在确认点怎样回复

### 内容准确，继续

确认应对应 Agent 刚展示的具体版本，并由相应角色作出。例如实际具有该角色的人员可以回复：

```text
作为本模块负责人，确认你根据工程证据提出的本轮 L1 等级及刚展示的 Spec/AC 版本。
没有需要修改的业务规则，请继续规划、实现和验收。
```

Agent 应记录本次确认来源与版本，然后自动继续，不再逐项询问“要不要生成 Plan”“要不要拆 Tasks”。如果项目已有其他人的可信确认记录，可以提供记录引用，由 Agent 核对范围和版本。

### 内容需要调整

```text
AC-002 不准确：未传状态时要保持所有原有查询条件和排序。
请修订当前 Spec，说明受影响的方案和测试，再让我确认。
```

Agent 修订同一个活跃变更，并重新展示关键变化；不会静默放宽 AC，不会每次反馈都创建一份新需求。

### L2 的额外确认

Agent 可以先起草 Spec/AC 和 Plan，一次展示全部待确认内容。需求确认和技术确认分别标明角色与范围；已有有效确认不重复请求。关键技术方案确认后，再自动推进 Tasks/Analyze/Implement 和契约/集成验证。

### L3 的额外确认

先完成 Spec MR 的需求、技术和适用专项确认，合入后提供 MR 与确切基线。Agent 再从同一变更目录推进实现 MR。它不能把聊天里一个笼统的“继续”当作 Spec MR 已合入，开发任务也不授权生产操作。

## 5. 确认后你还要做什么

Agent 自动做工程步骤与可执行检查，你负责核对业务含义、明确的人工验收和最终交付：

| Agent 提交的结果 | 人工需要核对 |
|---|---|
| 代码变化与 Spec/AC 对照 | 是否符合真实需求，边界是否遗漏 |
| 实际测试、退出状态、AC 结果 | 必需行为是否真的验证，失败/跳过/旧证据是否被正确处理 |
| 人工验收步骤和未验证项 | 在允许环境验证实际功能，记录结果 |
| MR 描述与内部证据引用 | 通常由另一位开发者审核，合并人核对最终版本 |

团队 GitLab 无自动 CI 触发。**人工发起入口后，Agent 可以在允许环境执行已有 Maven 命令和验收检查器**；不要求你手工键入每条测试命令。无法执行时必须说明具体缺口，不能输出伪造的通过结论。

风险评估目前由 Skill 指令约束 Agent，并由负责人/Reviewer 核对；还没有已验证的确定性风险分类器或 GitLab 强制评级门禁。自动项通过仍是待审核，Converge 也不等于实际测试。L0 无行为变化任务可复用已有检查，不强制生成完整 Spec、映射或新测试。

## 6. 暂停、换工具和结束

- 有关键业务疑问、风险升级、技术方案变化或环境阻塞时，Agent 应指出具体问题与影响，再请求必要确认。
- 换 Continue 插件或 Qoder App 时，提供活跃目录和已有记录：继续本轮变更，读取 Spec/Plan/Tasks、具体确认版本与实际测试结果，不重新起草第二份需求。
- 推送、对外评论、合并和生产操作仍按已有授权与平台权限执行。没有能力时可自动准备草稿，由人操作平台。
- 整个变更完成后 Spec 保留为历史；新需求新建增量记录，长期设计、接口和必要 ADR 随变化维护。

维护者/Reviewer 需要更多细节时，查看 [原生接入说明](skill-integration.md)、[Maven 验收契约](acceptance-contract.md)、[GitLab 验收路径](gitlab-manual-verification.md)和[MR 模板](../.gitlab/merge_request_templates)。

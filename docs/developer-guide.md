# 开发者使用说明：L0～L3 任务工作流

版本：0.1 · 2026-10-10。面向开发者、模块/技术负责人和 Reviewer。

日常开发从本页开始；方案依据见 [主设计](technical-design.md)，角色与流程规则见 [团队操作基线](team-operating-profile.md)。本页说明怎样操作，不新增另一套开发框架。

当前可用的是操作规则、MR 模板和实验验收检查器。团队 Preset/Workflow 尚未封装，Continue 自研插件与 Qoder 独立 App 尚未完成验证；下面的确认点暂由开发者主动执行。GitLab 无自动 CI 触发，验证命令由人发起，交付由 Reviewer 核对。

## 1. 先选任务等级

让 Agent 先读取当前代码、测试、项目规范与需求，给出建议等级和风险依据。负责人确认后按下表操作；不能按代码行数或“只是修 Bug”判定低风险。

| 等级 | 典型任务 | 谁确认等级 | 编码前确认 | MR 路径 | 必留产物 |
|---|---|---|---|---|---|
| L0 | 局部、可逆、不改业务契约的小修复/调整 | 模块负责人 | 短变更意图与验证方式，可引用明确 Issue | 单 MR | Mini-Spec、实际验证与 Review |
| L1 | 单模块、边界清楚的常规行为变更 | 模块负责人 | 具体版本的 Spec 与 AC | 单 MR 分阶段 | 增量 Spec、Plan/Tasks、AC 映射、证据 |
| L2 | 跨模块、公共接口、数据库结构、并发一致性 | 技术负责人 | Spec/AC + 技术方案具体版本 | 单 MR 分阶段 | L1 产物 + 影响分析、契约/集成验证 |
| L3 | 权限安全、资金、敏感数据、不可逆操作、重大迁移 | 技术负责人 | Spec/AC/方案 + 适用的专项确认 | Spec MR + 实现 MR | L2 产物 + 风险、预演、发布与恢复方案 |

一行权限修复也可能属于 L3。数据库结构变更初始至少按 L2 评估；破坏性迁移或敏感数据风险提升到 L3。具体业务边界由负责人确定。

发现新风险：先停止相关实施，记录影响，请对应负责人确认新等级与所需控制。降级由降级前等级对应的负责人留痕；跨 L2/L3 降到 L0/L1 仍需技术负责人批准。

## 2. 开始前确认工程已就绪

首次接入工程由维护者按[工作电脑验证手册](work-mac-validation.md)处理。日常开发先检查：

- 当前业务仓库、分支、需求来源正确，已有修改的归属清楚。
- 项目已有 Constitution、AGENTS.md 或等价规范，明确测试入口和活跃变更位置。
- 客户端已验证如何调用原生指令/Skill，或明确只支持手动引用。Continue 上游、Qoder CLI/IDE 的结果不能代替实际插件/App。
- 知道模块/技术负责人和最终 Reviewer；最终交付通常由另一位开发者审核，例外需显式记录。
- 能运行项目原有 Java/Maven 测试，清楚 profile、模块、Surefire/Failsafe 配置与报告路径。

不要在每个需求开始时重新初始化 Spec Kit、重建 Constitution 或安装组件。首次初始化的已核验步骤见[原生能力记录](research/native-capability-audit.md)。

### 原生能力怎么调用

以下名称来自本仓库在 Spec Kit 1.1.2 generic Skills 探针中实际生成的入口。它们是能力名称，不是统一的终端命令；在已验证的客户端入口中调用，具体 Slash 语法按实际集成确定。

| 工作 | 原生入口名称 | 产物/作用 |
|---|---|---|
| 起草需求 | speckit-specify | 当前变更 spec.md |
| 澄清规则 | speckit-clarify | 补齐 Spec 中的未知业务规则 |
| 规划方案 | speckit-plan | plan.md 与适用设计产物 |
| 拆分任务 | speckit-tasks | tasks.md |
| 检查实施前一致性 | speckit-analyze | 检查 Spec/Plan/Tasks；L2/L3 在实施前执行 |
| 实施 | speckit-implement | 按已确认范围与任务实现 |
| 检查实现遗漏 | speckit-converge | 对照实际代码检查遗漏并追加剩余任务 |
| Bug 专项能力 | speckit-bug-assess、speckit-bug-fix、speckit-bug-test | 安装官方 Bug Extension 后评估、修复、验证 |

当前默认 speckit Workflow 不含 Converge 和实际测试，应分别显式执行。原生 gate 的本地 approve 输入不代表可信人工批准；确认依据保留在 GitLab MR 或团队批准的记录中。内部 GitLab 流程不调用面向 GitHub 的 taskstoissues。

## 3. L0：Mini-Spec → 确认 → 修复 → 验证 → Review

适用示例：局部空值处理修复，保持已有业务错误和接口契约。以下示例均为虚构任务，不能直接作为真实业务批准。

1. **开发者让 Agent 分析。**说明当前问题，要求先查代码/测试，列出影响面、等级理由与未知项，暂不改业务代码。Bug 可先使用官方 assess 能力。
2. **保留 Mini-Spec。**用 [L0 模板](../.gitlab/merge_request_templates/L0-Mini-Spec.md)在 Issue 或本次 MR 写明目标、期望、范围外、风险理由、验证方式和确认来源。不要求完整 feature Spec。
3. **模块负责人确认等级，开发者确认变更意图。**确认可引用已有明确 Issue；若规则不明确，先补齐记录。
4. **让 Agent 做最小实现。**行为缺陷按需要补回归测试；无行为变化的调整可复用现有检查，并写明无需新增测试的理由。
5. **人工发起验证。**运行已有测试/构建，保存被测版本、工作区状态、命令、退出码与原始结果。L0 不强制创建 acceptance.json 或调用 AC 检查器。
6. **同一个 MR 完成交付审核。**Reviewer 核对意图、风险和实际验证；有权限的合并人检查后合并。

可以给 Agent 的起始说明：

```text
请先分析这个问题，读取当前实现、测试和项目规范，暂不修改业务代码。
提出建议风险等级与依据，列出未知规则，并起草可放入 MR 的 Mini-Spec：
目标、期望行为、范围外、影响面、验证方式。等待人工确认后再实施。
```

**L0 完成条件：**有变更意图依据、等级确认、实际验证结果和最终人工审核。Chat 修复同样保留记录。

## 4. L1：同一个 MR，先确认 Spec/AC，再实施交付

适用示例：单模块增加查询过滤条件，接口兼容、边界和验收明确。

1. **起草增量 Spec。**在新变更目录使用 Specify/必要 Clarify，开发者补充真实业务规则。在原生验收场景中加稳定 AC ID，格式见[验收契约](acceptance-contract.md)。
2. **建立单个 MR 的确认阶段。**建议开 Draft MR，先提交 Spec/AC。使用 [Spec-Review 内容](../.gitlab/merge_request_templates/Spec-Review.md)作为描述中的“实现前确认”区段；不另开 Spec MR。
3. **人工确认具体版本。**模块负责人确认等级，业务/模块负责人确认目标、边界与 AC。在 MR 留确认人、时间、提交及文件摘要。关键未知规则未解决时暂停。
4. **生成精简 Plan/Tasks。**优先复用原有架构和测试。必要时 Analyze；若规划发现 AC、范围或关键设计须变化，先重新确认受影响内容。
5. **实施并维护验收映射。**使用 Implement，编写/复用实际测试；acceptance.json 只记录 AC 引用和报告选择器，不复制需求全文。初次生成映射时核对真实报告名称，之后每轮交付使用最新映射重跑验证。
6. **显式 Converge，然后实际验收。**发现遗漏回到实现；Converge 完成不等于测试通过。按第 7 节运行项目测试和检查器，完成明确的人工项。
7. **仍在原 MR 审核交付。**追加 [Implementation-Review 内容](../.gitlab/merge_request_templates/Implementation-Review.md)，引用确认阶段与验收记录。保留原确认评论；Reviewer 核对最终被测版本和业务逻辑，再按权限合并。

可以给 Agent 的起始说明：

```text
本任务建议按 L1 处理，等级由模块负责人确认。请调用项目已接入的原生
Specify/Clarify 能力，起草本轮增量 Spec 和带稳定 ID 的 AC；暂不实现业务代码。
列出需要我补充的规则。人工确认具体 Spec/AC 版本后，再推进 Plan/Tasks 与实现。
后续交付需要显式 Converge、实际测试、AC 验收证据和另一位开发者的审核。
```

**L1 完成条件：**单 MR 中可追溯到已确认 Spec/AC 版本、实现、当前验收证据、人工项和最终 Review。关键内容变更后重新确认。

## 5. L2：同一个 MR，增加技术方案确认

适用示例：两个模块之间演进接口，或进行非破坏性表结构变更。先由技术负责人确认实际等级；高风险情形升级 L3。

1. **按 L1 起草并确认需求。**技术负责人确认风险等级，业务/模块负责人确认 Spec/AC。
2. **先完成技术方案。**使用原生 Plan 记录影响模块、接口/数据兼容、并发与幂等、必要迁移/恢复思路、契约/集成测试范围。内容按实际风险裁剪。
3. **在同一 MR 确认技术方案具体版本。**由技术负责人留痕；需要专项意见时按职责补充。确认前只推进分析与方案，不实施相关业务变更。
4. **Tasks → Analyze → Implement。**任务拆分后做实施前一致性检查，处理重要缺口。影响方案、范围或 AC 的变化先重新确认。
5. **Converge → 手动验收 → Review。**执行受影响模块和必要契约/集成测试；映射显式声明模块与报告集合。不能只运行一个模块的单测后声称跨模块验收完成。

可以在 L1 起始说明上增加：

```text
本任务建议 L2，由技术负责人确认等级。请在原生 Plan 中明确影响面、
兼容性、必要集成/契约验证与恢复思路。业务 Spec/AC 和技术方案都要确认
具体版本后再实施；使用单 MR 分阶段，实施前完成 Tasks 与 Analyze。
```

**L2 完成条件：**L1 条件 + 技术方案确认、影响面验证和相关长期设计/接口/ADR 同步；仍是一个 MR。

## 6. L3：Spec MR → 实现 MR → 专项验收

适用示例：权限边界调整或重大数据迁移。开发验收与生产执行分别控制。

1. **建立 Spec MR。**技术负责人确认等级；先提交 Spec、AC、Plan 及必要 Tasks、专项风险、隔离预演、发布与恢复方案。使用 [Spec-Review 模板](../.gitlab/merge_request_templates/Spec-Review.md)。
2. **完成需求、技术及适用专项确认。**明确关键风险、实施边界、验收方法与执行权限；记录确切版本。Tasks/Analyze 暴露关键方案变化时重新确认。
3. **按权限合入 Spec MR。**这一合并只确立实施基线，不代表整个需求已交付，活跃 Spec 也未冻结为历史。
4. **从已合入基线开实现分支和实现 MR。**引用已批准的 Spec MR、合并后的 Spec/Plan 文件版本与确认记录。继续同一个变更目录，不重新 Specify 生成第二份需求。
5. **分阶段实施与隔离验证。**按已确认任务执行，显式 Converge，运行实际测试、预演和专项验收。范围、AC 或关键方案变化时停止相关实施，将修订及重新确认关联到实现 MR；不篡改原批准记录。
6. **独立审核交付。**使用 [Implementation-Review 模板](../.gitlab/merge_request_templates/Implementation-Review.md)，完成技术/适用专项复核、人工验收和最终版本核对。需要生产发布或数据操作时另按现有权限执行。

可以给 Agent 的起始说明：

```text
本任务建议 L3，由技术负责人确认等级。先准备独立 Spec MR 的产物：
Spec/AC、技术方案、必要任务与专项风险、隔离预演、发布及恢复方案。
暂不实施业务或生产操作。Spec MR 完成适用人工确认并合入后，
再从该基线开启实现 MR，引用确切版本。任何新的风险或关键变化先上报并重新确认。
```

**L3 完成条件：**批准基线与实现 MR 可追溯，专项验证和最终审核齐备。开发完成、预演完成、生产执行完成分别报告；未授权的生产操作不能由 Agent 推进。

## 7. 所有等级共用的确认与验收动作

### 确认怎样留痕

在 MR 或团队批准的内部记录中填写以下内容。由对应人员实际确认；Agent 可以整理草稿，不能代替确认人发表结论。

```text
变更 ID / 等级 / 风险理由：
确认类型：等级 / 需求与 AC / 技术方案 / 专项
确认范围：Spec/AC/Plan 的文件路径、具体提交与文件摘要
确认人 / 角色 / 时间：
结论与附加条件：
未决问题及是否影响实施：
```

确认的是内容版本。后续实现提交改变 MR head，不会仅因 SHA 不同就使未变的 Spec/AC 内容确认失效；但必须核对内容，关键内容变化后重新确认。平台可能要求重新审批，遵守实际配置。

### Maven 验收怎样执行

L0 可直接复用现有检查并填记录；L1～L3 在报告布局适配通过后使用实验检查器。完整命令与前置条件见 [操作说明](../scripts/README.md)，下面从标准仓库根运行，替换为真实内部路径和批准的项目命令：

```sh
python3 scripts/verify_maven_acceptance.py \
  --repo /path/to/business-repo \
  --mapping specs/001-change/acceptance.json \
  --output /path/to/internal-evidence/run-001.json \
  -- ./mvnw clean verify
```

执行前提交本轮代码、测试、Spec 和映射，使业务仓库工作区干净；报告目录应被忽略。输出文件必须尚不存在，保存到内部批准位置。命令与 profile 沿用工程实际配置；verify 不保证已经配置 Failsafe 或运行全部集成测试。

检查器只支持 Maven 默认报告布局和显式模块集合，真实工程待验证。Python/报告布局不支持时记录受限，先保留原有测试与人工核验路径，不能伪称 AC 检查器通过。

**读结果时注意：**退出码 0 只表示当前模式的自动检查通过，delivery_status 仍为 requires_review；非零按失败处理。reports-only 模式不证明当前版本、新鲜度或实际执行，不能用于最终交付。

### Reviewer 最后核对什么

使用[验收记录](../templates/verification-record.md)和实现 MR 模板核对：

- Spec/AC 与必要技术/专项确认都有身份、版本和来源，等级没有低估。
- 代码与业务意图一致，测试断言有效；必需测试实际执行，人工项有真实结果。
- 原始报告、命令退出状态、被测提交及 Spec/映射摘要对应；跳过、缺失、旧报告与零测试没有当作通过。
- 最终 MR head 与被测内容一致。测试后改变代码、测试、POM、配置、AC 或映射时，重跑受影响验证。
- 只有证据链接/说明更新时，明确该变更不影响被测内容，保留原始被测提交；不能把报告补交掩盖成代码已经验证。
- 通常由另一位开发者完成最终审核；例外说明原因、确认人及替代复核方式。

GitLab 无自动 CI 时由合并人核验这些条件后按权限合并。模板、Agent 指令和本地 gate 都不能单独阻断合并。

## 8. 中途变化、结束与接力

| 情况 | 开发者操作 |
|---|---|
| 业务规则不清楚 | 暂停相关实现，补充 Spec/AC 并请人确认 |
| AC、范围或关键方案变化 | 修订当前活跃变更，重新确认版本，同步 Plan/Tasks 与映射 |
| 发现更高风险 | 停止相关实施，上报对应负责人；升级到 L3 时补齐 Spec MR/实现 MR 路径并关联已有记录 |
| 实现遗漏或测试失败 | 修复、显式检查遗漏、重跑验证，不放宽 AC 伪造通过 |
| 环境、权限或报告布局不支持 | 记录 blocked/unverified 与具体缺口，继续允许且不受影响的工作 |
| 紧急例外 | 由指定负责人确认原因、影响检查、替代验证和补全期限；细则未定不等于自动豁免 |
| 切换 Continue 插件 / Qoder App | 提供当前目录、已确认版本、Plan/Tasks、实际验证结果与剩余项，不只转述 Chat |
| 整个变更完成 | 保留 Spec 为历史，更新必要长期设计/接口/ADR；下一次需求新建增量记录 |

历史 Spec 不持续追随所有后续代码变化。新需求或 Bug 以当前代码、测试、接口和长期设计为依据，用链接说明前序关系；不要补写全系统 Spec。

更详细的平台证据处理见 [GitLab 手动验收路径](gitlab-manual-verification.md)，现场复现案例见[验证清单](validation-cases.md)。

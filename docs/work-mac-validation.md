# 受 MDM 管控工作 MacBook 验证手册

用途：让工作电脑主要做环境和流程验证，避免重新讨论基础路线。状态：验证计划，尚未在受管电脑执行。测试结果和内部信息只保存到团队批准位置。

## 1. 两台电脑的分工

| 个人电脑阶段 | 工作电脑阶段 |
|---|---|
| 形成主设计、默认规则、模板与原生版本证据 | 确认真实工具、网络、运行环境和 GitLab 权限 |
| 用虚构样例/隔离项目验证原生文件生成 | 用批准的业务试点验证真正的行为和验收结果 |
| 准备公开发布物、版本及说明 | 按步骤记录 pass/fail/blocked/unverified |
| 不处理公司源代码、凭证与真实业务日志 | 不把内部资料上传公开仓库或个人环境 |

个人电脑跑通不计为工作环境通过。客户端和平台权限的事实无法预先保证；遇到限制时记录原因与允许的替代路径，不更改 MDM、安装来源、证书、网络策略或设备保护来绕过限制。

## 2. 取得材料与固定版本

1. 通过公司允许的 GitHub 访问/下载方式获取明确 tag 或 commit；若禁止直连，使用公司允许的内部镜像或文件导入方式。
2. 对照发行说明核对版本与文件。ZIP 中没有 Git 元数据时记录下载版本/归档摘要；需要业务 Git 流程验证时使用正常业务仓库，不能把解压目录误当 Git 仓库。
3. 先读 README、主设计 2.4 节、团队操作基线、GitLab 手动验收路径与版本核验记录。
4. 不将个人电脑的 .venv、绝对路径、临时源码或本地日志当作可移植环境。

## 3. V0：只读预检查

先记录以下结果，不安装新工具、不改业务项目：

- 仓库材料版本，当前可用 Git 和 Python 版本；Spec Kit 1.1.2 的源声明要求 Python >=3.11。
- AC 检查器独立使用 Python 3.9+ 标准库与 Git，无需安装 Spec Kit 的 Python 依赖；此要求与 Spec Kit >=3.11 分开核对。
- Java/JDK、Maven/Wrapper、Spring Boot、测试框架、Surefire/Failsafe 实际版本、profile 与报告布局。
- 公司是否允许安装/运行 Python 工具及依赖，是否有批准的软件源或内部镜像。
- Continue 自研插件的实际版本/源码基线、规则与自定义入口可用性。
- Qoder 的准确产品名称与独立 App 版本；不得用 IDE/CLI 截图代替。
- 工作电脑可访问的模型服务、安装来源和辅助脚本；只记录允许的资源，不收集 token 或设备管理详情。
- GitLab 实际版本/tier、MR、保护分支、审批、Runner/手动 Pipeline 能力；不以“无法自动触发”推断其余全不可用。

Python 不满足或安装被限制时，标记工具运行受限。仍可阅读规范、验证客户端加载明确的指令文件、人工生成/补充 Spec 并执行项目已有测试；这只能证明部分流程可用，不能称 Spec Kit CLI 集成通过。

## 4. V1：原生安装和生成验证

仅在公司允许时，在隔离目录创建工具环境和空白样例项目。使用已核验版本与官方方式，遵守批准的软件源；本仓库不提供自动安装或提权脚本。

依照 [原生能力核验](research/native-capability-audit.md) 中实际测试过的命令重现 generic 初始化、原生 Skill/命令产物与官方组件安装。先在空项目试，后续已有项目采用隔离分支并检查 diff。

随后按 [Skill 接入说明](skill-integration.md)安装 team-sdlc，核对默认 start 入口、四个兼容入口和共享资源；先验证无需人工预评级、低级入口不能绕过风险评估，再进行下一节的实际客户端行为验证；生成文件本身不算业务流程成功。

验收：命令能运行，受管文件布局符合记录，引用脚本存在；必要失败条件能被发现。工具安装/产物生成成功不等于 Agent 成功执行需求。

## 5. V2：两个实际客户端验证

使用 [工具兼容矩阵](research/tool-compatibility.md) 与 [验证案例](validation-cases.md)：

1. 在 Continue 自研插件中发现/显式加载原生入口，验证规范与活跃变更定位。
2. 在 Qoder 独立 App 中导入/发现原生 Skills 或允许的薄适配入口。
3. 分别运行一个低风险虚构任务，检查澄清、人工暂停/确认、恢复、文件写入与已有测试执行。
4. 在两种客户端之间接力同一活跃变更，只依赖仓库产物继续，检查历史 Spec 和分支切换。

若客户端只支持手动引用文件，记录为 manual-reference；不得记为自动发现成功。若命令运行依赖不可用 CLI，记录为 blocked，不自行换成另一产品后宣布通过。

## 6. V3：GitLab 手动验收与真实试点

按团队操作基线的已批准规则，用一个 L0 和一个 L1 任务验证完整闭环，再补一个 L2 案例。首次业务试点前由负责人确认实际 AC 和操作规则。

先按[检查器操作说明](../scripts/README.md)在虚构样例运行自检与报告诊断，再在批准的真实工程使用默认运行模式。缺少 Python 或布局不支持时记录受限，保留原有测试与人工核验路径，不能伪称检查器已通过。

对照 [GitLab 手动验收路径](gitlab-manual-verification.md)，生成版本绑定证据、提交 MR、由 Reviewer 核对和合并。没有自动 CI 不影响执行测试，但必须据实报告自动约束的缺口。

在无关紧要的隔离 MR 中核验未批准、证据过期和修改后审批等失败案例；平台不支持强制拦截时记录人工发现结果，不测试破坏生产权限。

## 7. 结果记录与回传

每个案例记录：案例 ID、材料版本、产品版本、操作步骤、预期/实际、状态、证据的内部位置、限制与建议。模板见 [验证结果模板](../templates/workstation-validation-record.md)。

- pass：在指定环境实际执行，满足预期。
- fail：实际执行但结果与预期不符。
- blocked：已确认缺少允许的工具、权限或资源。
- unverified：尚未执行或信息不足。

工作电脑应优先产生“能力兼容性、失败步骤、影响范围”的结论。反馈公开仓库时仅提供经批准的脱敏通用问题；公司代码、内部链接、凭证、原始日志、截图和业务 Spec 均不直接回传。是否允许对外反馈按公司规定执行。

## 8. 现场只需确认的事实

方案方向、角色原则和验证步骤在个人电脑准备。现场仍必须确定真实版本、允许安装来源、插件加载能力、GitLab 强制能力、试点业务 AC 与负责人身份。这些是实际输入，不是重新选框架的理由。

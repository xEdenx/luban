# Codex 实施任务接力说明

版本：0.5 · 2026-10-10（Asia/Shanghai）
主设计依据：[Agent-Native Development 团队转型方案](technical-design.md)

面向开发同学的日常入口为 [L0～L3 使用说明](developer-guide.md)。本文件用于继续完善标准与环境验证。

## 1. 接力目标与当前状态

将已确定的团队转型方向落到实际工程：**最大程度复用 GitHub Spec Kit 1.x 原生机制，采用 Flow-forward 增量一次性 Spec、L0–L3 风险分级、AC-to-Test 可执行验收、AGENTS.md + Skills + CI，并在试点验证后使用官方 Bundle 标准化。**

团队现有客户端是基于 Continue 自研的 VS Code 插件，以及 Qoder 独立 Coding Agent App。不得用 Continue 上游、Qoder CLI、Qoder IDE 或 QoderWork 的支持情况替代实际客户端验证。

当前已建立独立标准仓库，并完成部分 T0 核验：在个人电脑隔离环境安装 Spec Kit 1.1.2，验证原生文件生成、官方组件安装和虚构 gate 行为。已另补 Maven AC-to-Test 0.1 实验检查器及虚构自检，真实 Java 工程尚未运行。实际进度以 docs/memory.md 为准。尚未提供业务试点工程、插件源码和版本，尚未完成真实客户端验证、业务工程门禁、团队 Bundle 或生产操作。没有已经建好的内部 Bundle。

主文是设计依据，本文件是实施任务清单。优先修订这两份文档或目标仓库现有文档，不再生成一套内容重复的总方案。

当前已实现 [team-sdlc Extension](../extensions/team-sdlc/extension.yml)统一入口与四级兼容路径。先按工程证据和规则下限评估风险，不要求开发者预先评级；任何入口均不得绕过，负责人确认、Plan/实施/diff 复评和最终 Review 复核。它以当前 Agent 会话衔接原生能力，尚未完成客户端行为验证。维护者按 [接入说明](skill-integration.md)安装，开发者只提供需求/增量描述、回答必要问题并确认内容，Agent 自动生成 Spec 并在确认后继续实施和验收。不要重新改成开发者逐条调用命令。

### 当前工作模式：个人电脑准备，受管工作电脑验证

当前优先在个人电脑完成原生能力核验、可公开的规则、模板和验证手册。团队使用自部署 GitLab 且无法自动触发 CI；T2/T3 第一版改为人工执行同一验收契约，再由 GitLab MR Reviewer 核对证据。CI 是可替换的执行入口，不以升级 GitLab、自建 Runner 或开发 CI 服务为前提。

工作电脑按 [验证手册](work-mac-validation.md) 检查真实客户端、MDM 允许的工具/网络和内部 GitLab 权限。没有条件验证的项目标记受限，不绕过管控、不把个人电脑结果替代工作环境结果。公开仓库不接收内部报告、业务代码或内部地址。

默认操作规则见 [团队操作基线](team-operating-profile.md)。已决策路线、建议默认值和待现场采集的事实分别标记，避免在工作电脑重新设计整套方案。

## 2. 直接继承的决策

- 不重新横向评选开发框架。Spec Kit 是基座，团队规则使用原生扩展点融入。
- Flow-forward 是团队生命周期约定：活跃变更可修订并重新确认，完成后冻结为历史，后续变更新建记录。
- 全局约束与长期设计采用 Living Spec 式持续维护，每类规则只有一个权威来源；权威映射、冲突处理、变更确认与约束版本追溯按[主设计第 4 节](technical-design.md#4-混合生命周期flow-forward-与-living-spec)。ADR 保留历史，进度记录不覆盖规则。
- L0–L3 已确定；L0/L1 模块负责人、L2/L3 技术负责人确认等级，降级需相应负责人留痕。具体身份与阈值现场明确。L0 允许 MR Mini-Spec，不能无记录交付。
- 人工确认业务意图与 AC，再实施并验收；复杂任务增加技术和专项确认。
- AC-to-Test 的价值在实际执行和可追溯证据，不是文件数量、测试名称或模型自评。
- AGENTS.md 引导行为，Skills 提供专项知识，CI 与 Git 权限控制交付。Workflow gate 不自动成为可信授权机制。
- Bundle 留到经过试点的标准分发阶段，避免先开发框架再寻找需求。
- L1 已决定使用单个 MR 分阶段：先确认 Spec/AC 的具体版本，再实现，最后审核交付。
- L2 已决定单 MR 分阶段并确认技术方案；L3 为 Spec MR + 实现 MR。
- 最终交付通常由另一位开发者审核；特殊情况明确记录例外。
- 首版适配 Java 后端、Maven、Spring Boot；实际 JUnit/插件版本与报告布局仍需核验。

若真实环境无法实现某项决策，先给出证据、最小替代方式和影响，再请负责人裁决；不要默默改路线。

## 3. 实施方法与权限边界

按“官方原生能力 → 配置/组合 → 薄适配 → 必要扩展”的顺序工作。每项自研内容说明为何原生能力不足，并复用已有脚本目录和 CI。

先核验精确版本和命令帮助，再写可执行安装步骤。不直接复制旧对话中的 `--force`、初始化选项或 Slash Command；`/speckit.*` 与 CLI 管理命令的角色不同，生成入口可能随 integration 改变。

在隔离分支或测试副本试验初始化，保留已有文件。存在未提交改动时先辨明来源，不覆盖、不重置。全局工具、客户端配置及外部平台权限的修改按届时用户授权进行；实际生产部署、合并、生产数据变更不包含在本文移交本身的授权中。

先检查项目已有的 AGENTS.md、交接记录、技术设计和 ADR 等价文件；按适用性补齐或记录例外。不要机械增加空文件或第二套项目状态系统。

缺少目标仓库时，采集仓库路径、Continue 自研插件版本/源码位置、Qoder App 产品版本和具体审批人；继承已确认的 GitLab、技术栈与审批原则，不重复询问。可先完成公开资料核验和设计差距分析；实际客户端操作没有条件时标为未验证。

## 4. 可执行任务清单

任务列表是设计基线，当前执行状态以 docs/memory.md 为准。按依赖推进；不把文档设计完成标成工程验证通过。

### T0：环境盘点与事实核验

**依赖：** 目标工程与工具信息；公开资料核验可先进行。

操作：

1. 读取目标仓库指南、构建配置、CI、测试报告格式和权限说明，确认技术栈及现有验证入口。
2. 核验 Spec Kit 的可用 1.x 版本；选择精确版本并记录版本/提交与来源。对照该版本检查 Core、Converge、Bug、Lean、Workflow、Integration、Bundle。
3. 记录实际 Continue 插件基线、定制点和规则/Prompt 加载方式；记录 Qoder App 的准确产品名称和版本。
4. 盘点平台可用的分支保护、必需检查、审批身份、修改后审批失效和绕过权限。不假设团队使用 GitHub Actions。
5. 把结果记录在目标仓库现有技术设计或一个最小实施记录中，引用主文决策。

验收：

- 形成“能力 → 原生机制 → 锁定版本证据 → 本地验证结果 → 差距”的表。
- 区分已运行通过、文档支持但未运行、不支持、缺少信息四种状态。
- 明确 P1 的最小改动和所需条件，不提出无证据的大型自研平台。

### T1：验证原生最小工作流

**依赖：** T0；优先在一个存量试点工程开展。

操作：

1. 在隔离环境初始化，检查生成文件和归属，复用官方模板；评估 Lean 与 Bug 组件是否适合实际任务。
2. 复用现有工程规范，必要时起草并人工确认最小 Constitution；在精简 AGENTS.md 中记录各类规则的权威路径、活跃变更入口、历史 Spec 边界、验证命令和重新确认规则。
3. 用团队 L0 入口验证 Mini-Spec 与 Review；调用 L1 入口，提供需求文档/增量描述，由 Agent 实际完成原生 Spec → 人工确认 → Plan/Tasks → Implement → Converge → 测试流程，不要求人逐条调度。
4. 人工补充真实业务规则并确认 AC；重要问题没有解决时保留暂停，不由 Agent 猜测为已批准。
5. 在活跃变更中演示一次范围/AC 修订，重新确认并同步受影响的 Plan/Tasks；结束后冻结记录。
6. 在批准的隔离案例中核对约束冲突时暂停、规则实质变化后复评，以及验收记录关联适用约束版本；分别记录模型行为与人工复核结果，不视为检查器自动门禁。

验收：

- 两种任务都留下需求依据、实施记录、测试结果和人工确认记录。
- Converge 发现剩余工作时能回到 Implement；没有用其输出替代真实测试。
- 不补写存量全系统 Spec，不复制原生流程到另一套 Skill。

### T2：定稿最小 AC-to-Test 契约

**依赖：** 个人电脑原型可用虚构 AC/报告先验证；正式适配仍依赖 T1 的真实 AC 与测试报告。

已有 [JSON 0.1 契约](acceptance-contract.md)与[检查器及操作说明](../scripts/README.md)，继续核验并最小调整，不重新实现一套。

操作：

1. 沿用原生验收场景，加稳定 AC ID；使用当前 acceptance.json 0.1 映射，不恢复早期 YAML 提案。
2. 对照真实 Maven 报告验证 schema：变更 ID、等级、Spec 路径、模块/报告集合、精确 testcase 身份、人工项原因/步骤。
3. 明确多模块、参数化测试和集成测试的标识与报告聚合规则；先适配实际框架，不为通用性开发多语言平台。
4. 验证已有最小确定性检查，比较“已确认 Spec 的 AC 全集”和映射，读取本次实际报告，处理失败、跳过、零测试、缺失与过期结果。
5. 当前手动运行记录实际被测 SHA、Spec/AC 摘要、命令/退出状态与报告链接；未来 CI 复用同一契约，人工项关联审核记录。

验收：

- 每个必需 AC 都能追溯到当前验证结果或明确待完成的人工验收。
- 只写测试名、只存在源码、模型声称通过均不能产生验收成功状态。
- Reviewer 检查实际断言能验证已确认语义；行为缺陷尽可能有修复前失败、修复后通过的证据。

### T3：把门禁接入现有交付流程

**依赖：** T2；平台配置需要相应权限和届时授权。

操作：

1. 按 L0–L3 整理 G1–G4：产物完整性、实现前确认、自动化验收、人工逻辑验收。
2. L1/L2 使用单 MR 分阶段，L2 增加技术方案确认；L3 使用 Spec MR → 实现 MR。验证版本绑定和实际约束能力。
3. 审批绑定具体 Spec/AC 版本。关键内容修改后重新确认，禁止以 Agent 可修改的 `status: approved` 作为独立证明。
4. 第一版手动运行 AC 检查与现有测试，按 GitLab 实际权限执行人工 Review 与合并核验；未来 CI 可用时再接同一检查。
5. 保护关键门禁配置，确认机器人和管理员绕过规则；定义负责人批准的紧急例外及补全时限。

最小负例验证：

| 输入或操作 | 预期结果 |
|---|---|
| Spec 中 AC 未映射，或映射引用不存在的 AC | 验收检查失败 |
| 映射测试未实际执行、被跳过、报告丢失或零测试 | 必需验收失败 |
| 已通过结果来自旧提交或旧 AC 版本 | 不能作为本次证据 |
| 未批准 Spec，或批准后修改关键内容 | 受控审批方案下不能通过交付门禁 |
| 在拟合入变更中删除必需检查 | 被权限/审核控制发现，不能静默绕过 |
| L0 无 Mini-Spec、无验证说明 | 完整性检查失败 |
| 合格的正常变更 | 手动验收与人工审核通过后按权限交付；将来可接 CI |

验收：

- 保存负例和正常例的实际结果；无平台权限时明确“配置待启用”，不声称强门禁已落地。
- 明确 CI 阻止合并与工具阻止写代码的区别。未经验证，不承诺软件能够证明本地代码生成发生在审批之后。

### T4：验证两种真实客户端及跨工具接力

**依赖：** T0 的版本信息，T1–T3 的仓库产物；工具入口探索可提前进行。

操作：

1. Continue 自研插件先试现有 Rules/Prompts 或实际保留的机制，必要时用很薄的入口连接原生指令。
2. Qoder 独立 App 按对应文档试导入/发现 Skills 与调用，验证工作区、路径、权限和恢复行为。
   安装团队 Extension 后验证统一入口、四兼容入口及共享参考可访问，尤其验证确认前暂停、确认后自动推进、修订恢复与交付核对。CLI Workflow + generic 实测不能派发，不能当作 App 自动执行方案。
3. 原生集成不适合时评估 generic 输出。记录真实生成入口，不假设文件出现就等于 App 可以调用。
4. 每种客户端至少完成一个真实变更的起草、人工补充/确认、实现、测试与结果检查。
5. 选一个变更在两种工具之间交接，依靠仓库产物定位范围和状态，检查分支切换后是否读取正确 Spec。

验收：

- 两个实际客户端分别有版本、步骤、产物与验证结果，不能用 Qoder CLI 结果代替 App。
- 工具入口只引用或受控分发同一套内容，未手工维护两份完整规范。
- 手动加载、部分支持与自动集成成功分别统计，未验证能力留在兼容矩阵中。

### T5：补充复杂任务与新工程试点

**依赖：** T1–T4 的基本闭环。

操作：

1. 使用一个真实 L2 场景验证技术确认、影响分析、契约/集成测试及文档同步。
2. 在新工程验证最小架构、工程原则、CI 与增量 Spec 的初始化路径。
3. L3 可先验证方案、审批、隔离预演与恢复流程；生产操作按单独授权执行。
4. 记录端到端耗时、人工纠错、首次验收结果和缺陷；按等级与工具版本统计。

验收：

- 一个存量工程和一个新工程都具备可重复的接入说明。
- 复杂变更的风险与证据明确；未做生产预演或发布的部分仍标未验证。
- 有实际数据支持哪些步骤保留、简化或删除，不预设效率提升百分比。

### T6：用官方机制标准化分发

**依赖：** T5；必要扩展经过真实试点证明。

操作：

1. 仅把稳定的模板裁剪放入 Preset，步骤组合放入 Workflow，新增检查放入必要 Extension。
2. 按锁定版本 schema 构建内部 Bundle，复用官方组件；确认 Skills、CI 和项目规则的受支持承载方式。
3. 锁定 CLI 与组件版本，记录文件归属、来源、兼容范围和项目覆盖规则。
4. 验证新工程安装、存量安装、重复安装、升级、移除、失败后的恢复和项目定制保护。
5. 发布最小使用说明与维护责任。团队内部发布包不得表述为官方认证的 Bundle。

验收：

- 两类工程能安装同一团队标准，客户端差异通过已验证入口处理。
- 有真实安装、更新与移除结果；不假设 Bundle 自带任意文件分发、权限沙箱或失败自动回滚。
- 回退方式可操作，长期业务资料和手工配置不被覆盖。

## 5. 每阶段交付格式与完成判断

每阶段简洁报告：

```markdown
阶段与状态：
原生能力复用：
必要新增/适配及理由：
修改的实际文件：
已执行验证与结果：
审批及证据链接：
未验证项、限制与剩余风险：
下一步及真正缺少的输入：
```

阶段完成后同步目标项目技术设计、交接记录与必要 ADR；原生来源、版本和差距保留在同一个实施记录中。不要每阶段创建一份内容重复的总方案。

从 T0 开始按证据推进。信息不足时先完成不依赖该信息的工作；需要业务确认或实际权限时只提出具体问题，不让 Agent 自己填成已批准。设计完成、脚本测试通过、客户端运行通过、平台门禁启用和生产验证通过应分别报告。

首轮闭环完成不要求先做 Bundle；全团队标准化推广完成则要求 T6。当前文件中的任务均待在目标环境实施。

# 团队操作基线

日期：2026-10-10。状态：L1/L2/L3 审批路径、等级确认/降级权限与通常独立 Review 已由用户明确确认；试点规模与例外操作细则待批准。技术路线已决策；本文件只收敛日常操作细则，不另建工作流框架。

开发同学按 [L0～L3 使用说明](developer-guide.md)操作。本文件记录规则与确认状态，不重复逐步流程。

已明确交互方式：开发者调用默认 start 入口并提供需求，无需预先评级；Agent 依据工程证据与规则下限评估风险，再起草规范产物、在必要确认点暂停、确认后自动继续工程步骤。人负责业务/技术准确性与最终功能/交付核对，不逐条调度原生命令。team-sdlc 为当前实验入口，真实客户端行为仍待验证。

## 1. 已确认与待批准的边界

已确认：Spec Kit 1.x 原生优先、Flow-forward、L0–L3、AC-to-Test、多工具兼容、GitLab 无自动 CI、个人电脑准备与受管工作电脑验证，以及 Java 后端/Maven/Spring Boot 为首版适配目标。

生命周期采用已确认的混合策略：业务变更 Flow-forward，全局约束与长期设计 Living Spec 式持续维护。每类规则的权威来源、冲突处理和约束变更规则以[主设计第 4 节](technical-design.md#4-混合生命周期flow-forward-与-living-spec)为准；本文件只维护日常操作细则。

建议采用下列默认值，负责人可逐条调整。未回复不等于批准；现场环境验证可以先在虚构案例与隔离样例中进行，不以试验输出替代业务需求批准。

## 2. 风险分级默认值

| 等级 | 默认判定 | 编码前最小确认 | 交付最小确认 |
|---|---|---|---|
| L0 | 局部、可逆、不改业务契约；无权限/资金/敏感数据/结构迁移影响 | 开发者确认短变更说明或明确 Issue | 非作者 Reviewer 检查 Mini-Spec 与验证 |
| L1 | 单模块常规行为变更，边界和验收清楚 | 业务/模块负责人确认 Spec 与 AC | Reviewer 审核业务语义、原始报告和变更版本 |
| L2 | 跨模块、公共接口、数据库结构、并发一致性或较大回归范围 | 需求确认 + 技术负责人确认 Plan | 指定模块负责人 Review，兼容性/集成验证 |
| L3 | 权限边界、资金支付、敏感数据、不可逆操作或重大迁移 | 专项负责人确认范围、设计、预演与恢复 | 专项验收、发布授权与实际执行分开 |

风险评估是任何入口的必经阶段，原 L0～L3 入口只表达建议，不能固定等级。Agent 检查实际需求与相关代码、调用点、接口、数据及测试，展示检查范围、命中规则、未知项和推荐依据，负责人据此确认。L0 必须有排除更高风险的正面依据；关键风险未知先调查/澄清，不按 L0 开工。工作说明复用现有 Spec/Mini-Spec，不增加独立评级文件。

Plan 明确影响面、实施发现新增影响、最终 diff/验收准备时复评；最终 Reviewer 复核实际变更与分级依据。当前这些是 Skill 与人工操作约束，没有已验证的确定性分类器或平台强制评级门禁。

多个条件同时出现时按最高风险。代码行数和“只是 Bug”不能作为降级理由。Agent 推荐等级并说明触发条件；L0/L1 由模块负责人确认，L2/L3 由技术负责人确认。新增风险先停止相关实施并上报。降级需降级前等级对应负责人留痕，跨 L2/L3 降到 L0/L1 仍需技术负责人批准。

## 3. 默认审批与 MR 路径

- L0：一个 Implementation MR；Mini-Spec 可直接写 MR，引用原始需求确认记录。
- L1：已决定使用一个 MR 分阶段确认。建议采用 Draft MR，在评论中记录已确认 Spec/AC 的具体提交与文件摘要，再开始实现，最后审核交付；平台能否强制仍待验证。
- L2：已决定单 MR 分阶段，先确认 Spec/AC 与技术方案的具体版本，再实施并审核交付。
- L3：已决定 Spec MR + 实现 MR，先合入已确认 Spec/Plan/AC，再在实现 MR 引用确切版本；补充适用的专项确认。
- 批准后的活跃 Spec 仍可修订；修改范围、AC、风险或关键设计时重新确认。整个变更交付完成后才冻结为历史。
- 开发者、业务确认人、技术确认人可以按团队规模兼任。最终交付通常由另一位开发者审核，此原则已确认；职责无法分离时显式记录例外，不伪称独立审核。
- 不创建独立审批服务；优先 GitLab 原生记录。平台无强制审批时，由指定合并人执行“无确认/无有效证据不合并”的操作规则。

单 MR 可以提高效率，但不能仅凭评论证明所有本地代码生成都发生在批准之后。双 MR 提供清晰批准基线，也不能证明本地生成的物理时间。

## 4. Spec 最小内容

L1 及以上沿用原生 spec.md、plan.md、tasks.md，不加独立 PRD 或第二套任务文件。Spec 至少明确目标、范围/非目标、当前行为依据、稳定 AC ID、关键边界、风险理由、待澄清问题和确认链接。

Plan 记录实现约束、复用的架构/框架、影响面、必要验证和恢复思路。L2/L3 补充所需专项内容，优先写入原生 Plan；需要长期保存的决策进入现有 ADR。

本轮尚未确认的业务规则不能由模型猜测填满。文档完整性检查只能发现结构问题，不能代替业务理解确认。

## 5. AC 与验证默认值

- 使用变更内稳定 AC ID，例如 AC-001；完整身份由 change ID 与 AC ID 共同构成。
- AC 描述业务行为，至少表达条件、动作、可观察结果；按真实风险补边界、异常、并发、兼容性。
- 优先复用现有测试和报告。当前实验契约采用 acceptance.json 0.1，读取 Maven 默认 Surefire/Failsafe XML，具体规则见 [验收契约](acceptance-contract.md)。实际版本与布局经现场验证后再稳定发布。
- 关键行为优先自动化。人工项必须有原因、操作步骤、实际结果、执行人与时间；不纳入“自动化验证通过”统计。
- 跳过、缺报告、零测试、旧结果、版本不一致均不得解释为必需验收通过。无行为变化且无需新增测试时，由 Reviewer 确认复用哪些现有检查。
- 正例证明流程可用，负例证明缺失能被发现；初期人工识别负例属于人工能力验证，不计为机器门禁成功。

## 6. 无自动 CI 的交付默认值

默认复用开发者工作电脑已有的测试入口；记录实际命令、退出状态与原始报告。验收记录绑定被测提交、Spec/AC 版本、适用约束的路径与提交或可复核快照、工作区状态，最终 MR Reviewer 核对。优先在无未提交改动的被测提交运行，不能用 commit SHA 掩盖脏工作区。约束基线当前由人工核对，检查器不自动验证。

只生成一次报告不够：被测实现、测试、依赖/配置或 AC 变化后重新执行相关验证。无代码变化的记录更新也应说明变化范围，避免将测试后的代码修改隐藏在报告补交中。

手动 GitLab Pipeline 若可用，可作为后续执行入口；若不可用，保持本地执行路径。二者使用同一 AC 与报告契约，不另建自研 CI 系统。

## 7. 例外、归档和指标

紧急例外必须有指定负责人确认、明确原因、受影响检查、替代验证和补全截止时间。L3 不以紧急为由默认取消现有生产权限要求。若实际无法获得审批，报告限制，不自动批准。

合并完成后 Spec 作为历史保留。新需求新建目录，沿用当前代码、测试、接口及长期设计；用链接表达前序关系，不全量重写旧 Spec。活跃变更取消时保留取消原因。

第一轮收集每个任务的等级、客户端版本、计划内人工确认、非计划纠错/接管、首次验收、总耗时和缺陷。先形成可解释基线，再决定推广；不预设效率提升百分比。

## 8. 讨论收敛记录

| 需要负责人确认的规则 | 建议默认值 | 状态 |
|---|---|---|
| L1 审批形式 | 单 MR 分阶段，先确认具体 Spec/AC 版本，再实现，最后审核 | 用户已确认；Draft 状态为操作建议 |
| L2 审批形式 | 单 MR 分阶段，确认技术方案 | 用户已确认 |
| L3 审批形式 | Spec MR + 实现 MR | 用户已确认 |
| 风险分级与降级权限 | L0/L1 模块负责人；L2/L3 技术负责人；降级需相应负责人留痕 | 用户已确认；具体身份现场明确 |
| 最终 Reviewer | 通常由另一位开发者审核；特殊情况记录例外 | 用户已确认 |
| 文档生命周期与权威来源 | 业务变更 Flow-forward；全局约束与长期设计持续维护；每类规则唯一来源，确认与验收引用适用版本 | 用户已确认；客户端行为与团队执行待验证 |
| 无自动 CI 路径 | 本地运行原有测试 + MR 人工核验 | 基于已确认限制提出，细则待确认 |
| 首版工程类型 | Java 后端、Maven、Spring Boot | 用户已确认；精确版本现场核验 |
| AC schema | JSON 0.1 + Maven 默认 XML，Python 标准库检查器 | 实验实现；真实工程待验证 |
| 试点规模 | 一个 L0、一个 L1、一个 L2；后续新工程与 L3 演练 | 待确认 |

工作电脑阶段应优先验证这些规则能否执行，反馈具体失败步骤和限制；只有新事实改变设计前提时，才回到本文件讨论调整。
